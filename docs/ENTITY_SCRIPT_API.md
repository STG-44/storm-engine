# Script entity lookup, deletion and notification control

The bounded Rust script runtime now exposes three original internal functions
without native declarations, with ASCII case-insensitive names:

| Function | Behavior |
| --- | --- |
| `IsEntity(object_or_aref)` | Integer `1` when the embedding host reports a valid entity, otherwise `0` |
| `DeleteClass(object_or_aref)` | Void; asks the host to erase that entity |
| `EntityUpdate(integer)` | Void; zero disables script attribute notifications, any nonzero integer enables them |

These follow `internal_functions.cpp::FUNC_IS_Entity_LOADED`,
`FUNC_DELETE_Entity`, `FUNC_Entity_UPDATE`, `DATA::Get(entid_t&)`,
`DATA::Get(int32_t&)` and the notification gate in `compiler.cpp`'s attribute
`MOVE` branch. The original compiler initializes its flag to true.

Entity IDs retain all 64 bits. References resolve to the underlying variable;
plain object copies retain the entity ID but own separate attributes. An aref
uses the ID captured when it was bound. As in the retained attribute API,
`GetAttributeN` produces an aref with zero ID. Neither lookup nor deletion
clears script attributes or rewrites aliases to an entity.

`Host::is_entity` and `Host::delete_entity` are explicit embedding hooks. The
diagnostic host forwards them to its real `storm-core::EntityManager`: deletion
invalidates immediately, repeated deletion is harmless and destruction remains
deferred until `new_lifecycle`. Pending entities can still receive attribute
notifications through the original teardown lookup. Reused slots reject stale
IDs. The standalone diagnostic host does not advance native lifecycles itself.

`EntityUpdate` belongs to persistent script runtime state, not an individual
entity. It spans calls, nested events and posted frames, and survives script
errors and `ClearEvents`. Independent runtimes and fresh `Program::call` entries
start enabled. Suppression still writes attributes and performs the same path
validation and value conversion; it suppresses only the script's notification.
Explicit native `AttributeReference::write` remains under the embedding host's
control. Calls to `EntityUpdate` do not require an entity host.

Invalid types, stale/expired aliases, missing hooks, wrong argument counts and
builtin redeclarations produce errors. In particular, the original integer
getter does not convert floats or strings. Failed C++ getter paths can leave a
scratch register unchanged; Rust rejects those calls rather than depending on
that register. Pointer values and unsafe stale attributes are not emulated.

## Diagnostic and verification

```sh
cargo run -p storm-script --locked -- \
  rust/crates/storm-script/fixtures/entity_lifecycle.c \
  --frame-ms 0,0 --report entity-script-state.json
python3 rust/crates/storm-script/reference/entity_api/generate.py
```

The newly written script obtains the existing diagnostic observer through
`PreviewShip`, suppresses writes across a posted event, re-enables notifications,
deletes the entity through a copied object, and confirms that the original
reference now reports invalid. Its report contains the complete attribute tree
and three notifications, including one during pending deletion. It returns
`19`, with `hd=548`, `silent=1`, `deleted=1` and `valid=0`.

Twelve tests cover persistent/nested/posted notification control, alias and
copy identity, array elements, native deferred deletion and slot reuse, input
errors, default hooks, fresh runtime isolation and the diagnostic scenario.
One test replays 32 sequences / 560 snapshots generated by compiling the
verbatim three native cases, four DATA methods and attribute MOVE notification
fragment under UndefinedBehaviorSanitizer. Stack/storage and core dispatch
targets are instrumented adapters; this oracle checks forwarded IDs, calls,
results and suppression, not the original entity manager or complete compiler.
The generator records hashes of every extracted body.

The complete game API remains unfinished. `CreateEntity`/`CreateClass` need a
registered class factory, pre-Init registration and failure cleanup; those are
the next lifecycle step. `SendMessage` still needs the original 64-bit pointer
result and additional VM/message bindings. None of these three functions,
original ship classes, or complete commercial game startup is claimed here.
